01 · what it does

Secrets for agents, without the leaks

Not a cloud vault and not a password manager: one sealed file on your machine, and a single command that hands a workspace to a process.

locket run

locket run pantahub/stage -- ./deploy.sh starts the command with that workspace's variables in its environment. Locket prints the workspace and a count, never a value, and exits with the command's code.

Projects & workspaces

A project groups what one agent or tool needs; its workspaces hold one environment each: stage, prod, a teammate's sandbox. Every project has a default, so locket run pantahub just works.

A desktop manager

Create projects and workspaces, add, edit, reveal and delete variables in a window built with Oriel: compiled views, no web view, no JavaScript. It manages the same vault as the CLI.

Values stay out of sight

Values come in on stdin, so they never sit in argv or shell history. The window masks them as •••••••• N chars until you click Show, and they're zeroed in memory when Locket is done with them.

One writer at a time

Several agents and the window can change the vault at once: every edit holds a lock from read to save, and saves are fsynced and renamed into place, so a crash leaves the old vault or the new one.

Local, and on every machine

No server and no account. Share one vault between your machines through NomadFS's swarm or any synced folder: each machine keeps a full copy, works offline, and the newest edit wins. The shared files only open with your passphrase. MIT licensed.

03 · how it works

From a paste to a process

A value goes in once, and from then on only names travel.

  1. 01

    Store it once

    Paste a value into the window, or pipe it to locket set pantahub/stage/PH_TOKEN. It's sealed into vault.enc with AES-256-GCM, under a key only your user can read.

  2. 02

    Organise by environment

    Group variables by project and workspace. Store them under the names your tools already expect (DATABASE_URL, OPENAI_API_KEY) and the same script runs against stage or prod by changing one word.

  3. 03

    Run with a workspace

    locket run layers the workspace's variables over the inherited environment and starts the command. --only narrows it to a few names; --prefix injects them as LOCKET_<NAME>.

  4. 04

    The agent works with names

    An agent lists what's available with locket ls and runs commands through Locket. The values reach the process it starts, not the transcript it writes.

04 · with agents

Tell your agent where the keys are

Store the variables once, then put this in AGENTS.md, CLAUDE.md or the task itself, instead of pasting a token into the chat.

an honest note

A convention, not a wall

  • What it does: keeps values out of the conversation, the logs and the command line, which is where they usually leak.
  • What it doesn't: an agent that can run shell commands as you could also run locket get.
  • What's next: an MCP server that offers run without get, so the boundary is enforced, not asked for.

05 · safety

What the seal protects

Locket is careful about the few things a local vault has to get right.

  1. AE

    Sealed at rest

    vault.enc is AES-256-GCM with a fresh nonce per save, safe to copy on its own into backups or sync folders. master.key sits beside it, readable by your user only; Locket refuses a key that group or others can read.

  2. LK

    Locked while it changes

    Edits hold an exclusive lock from read to save, reads a shared one while reading: concurrent agents and the window never lose each other's changes.

  3. FS

    Crash-safe saves

    A save writes a temp file, fsyncs it, renames it over the vault and fsyncs the directory. A power cut leaves the old vault or the new one, never a half-written file.

  4. US

    Your user is the boundary

    Anything running as your user can read both files. Moving the key into the OS keychain is on the roadmap.
